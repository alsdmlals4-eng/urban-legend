## 0. 문서 목적

이 문서는 CASE-01 실제 게임 UI를 **현장 조사 Surface + 공통 조사 디바이스 Shell + 재사용 가능한 탭/보조 컴포넌트 + 공통 데이터/입력 계약**으로 분리하기 위한 통합 설계 명세다.

이 문서는 새로운 사건 규칙을 만드는 문서가 아니다. 2026-08-11 사용자 승인 Decision들과 기존 저승역 사건 정본을 구현자가 한 번에 읽을 수 있도록 결합한다.

제품 코드, Scene, Control, GDScript, Save Schema, InputMap을 이 문서만으로 수정하도록 승인하지 않는다. 실제 구현은 이 문서 검토 완료 후 별도 구현 계획과 TDD/검증 게이트를 거친다.

### 1.1 해소된 정본 충돌

기존 저승역 콘텐츠는 실제 추리 진행을 **3장**으로 정의하지만, 새 플레이어 UI는 **5개 섹션**을 사용한다.

이는 다음처럼 해석한다.

```text
기존 로직 1장 → 1. 발생 조건 + 2. 피해자 연결
기존 로직 2장 → 3. 금지 행동
기존 로직 3장 → 4. 구출 절차
후속 참조      → 5. 회수 대응
```

5개 UI 섹션을 5개의 독립 진행 장으로 구현하지 않는다. 기존 4/5/5 슬롯과 8/9/10 후보 풀 및 최종장→구출 흐름은 유지한다.

## 2. 전체 UI 경계

CASE-01 조사 UI는 두 개의 최상위 플레이어 Surface로 나눈다.

```text
LocationInvestigationSurface
├─ 현재 장소 시각
├─ 현장 대화/서술
├─ 현장 선택지
├─ 조사 포인트
├─ 조사 방법/행동
├─ 행동 결과 피드백
├─ 팀 상태/기존 진행 피드백
├─ 조사 디바이스 진입
├─ [이동]
└─ 루메 호출 표시 (contextual only)

InvestigativeDeviceShell
├─ 공통 Header
│  ├─ 괴이기록국 / CASE-01 저승역
│  ├─ [기록]
│  ├─ [괴이 매뉴얼]
│  ├─ [지도]
│  └─ [현장으로 돌아가기]
├─ RecordsTab
├─ ManualTab
├─ MapTab
└─ LumeCompanion (화면별 노출 규칙 적용)
```

실제 Godot 클래스/Scene 이름은 구현 단계에서 현재 코드와 맞춰 정한다. 위 이름은 책임 분리용이다.

## 3. 공통 InvestigativeDeviceShell

### 3.1 상단 정보구조

플레이어-facing 상단 탭은 정확히 다음 세 기능을 기준으로 한다.

```text
[기록] [괴이 매뉴얼] [지도]
```

우측에는 `[현장으로 돌아가기]`가 있다.

금지:

- 독립 `[로그]` 탭
- `AI 로그` 명칭
- 독립 루메 전체 탭

`루메`는 탭이 아니라 조사 UI에 통합되는 보조 컴포넌트다.

### 3.2 열기/닫기

- 현장 조사에서 기록/괴이 매뉴얼/지도로 직접 진입할 수 있다.
- Shell을 여는 행위 자체로 조사 진행, 판정, 시간 경과, 저장을 발생시키지 않는다.
- `[현장으로 돌아가기]`는 Shell만 닫고 원래 현장 조사 문맥으로 복귀한다.
- Shell 내부 탭 전환도 저장/판정/시간 경과를 발생시키지 않는다.

### 3.3 상태 보존

Shell은 사용 중 다음 **UI 문맥 상태**를 보존한다.

RecordsTab:
- 현재 분류
- 선택 기록
- 목록 스크롤
- 본문 스크롤

ManualTab:
- 현재 UI 섹션
- 현재 추리문/의미 포커스
- 선택 슬롯
- 선택 후보 키워드
- 본문/후보 스크롤
- 아직 도메인에 확정되지 않은 순수 UI 선택 상태

MapTab:
- 마지막 선택 장소
- 지도 pan/zoom 또는 의미상 동일한 view state
- 상세 패널의 선택 상태

Shell:
- 마지막 사용 탭

다시 Shell을 일반적으로 열면 마지막 사용 탭을 기본으로 복원한다.

도메인 상태가 바뀌어 기존 선택이 유효하지 않을 때는 필요한 범위만 안전하게 갱신한다.

## 4. 현장 조사 Surface

### 4.1 역할

현장 화면은 플레이어가 **현재 장소에서 보고, 읽고, 선택하고, 조사하는 주 플레이 공간**이다.

현장 화면이 소유하는 의미:

- 현재 장소 배경/시각
- 화자/대화/서술
- 선택지
- 조사 포인트
- 조사 방법/행동
- 조사 직후 결과
- 팀 상태의 간결한 확인
- 기존 진행/대응 진입 피드백
- 조사 디바이스 진입
- `[이동]`
- 루메의 작은 호출 표시

### 4.2 소유하지 않는 것

현장에 별도 사본을 만들지 않는다.

- 전체 기록 아카이브
- 전체 괴이 매뉴얼 편집기
- 전체 지도
- 현장 전용 별도 장소 데이터
- 현장 전용 별도 이동 판정
- 로그/AI 로그
- 루메 독립 화면

### 4.3 조사 행동 흐름

```text
조사 포인트 선택
→ 가능한 방법/행동 표시
→ 행동 요청
→ 기존 도메인/runtime 판정
→ 결과 피드백
→ 갱신된 현장 상태 렌더
```

UI는 정답/성공 결과를 자체 계산하지 않는다.

## 5. 기록 탭

### 5.1 목적

`[기록]`은 획득한 조사 자료를 다시 읽고 서로 비교하는 **단일 조사 아카이브**다.

### 5.2 기본 구성

```text
┌ 분류·목록 ───────┬ 기록 상세 본문 ─────────┬ 메타·연결 정보 ───┐
│ 전체              │ 제목                     │ 획득 장소          │
│ 현장 기록         │ 시간 / 출처              │ 획득 시점          │
│ 증거              │                          │ 관련 인물          │
│ 증언              │ 기록 내용                │ 관련 장소          │
│ 통신·방송 기록    │ 텍스트 설명/요약         │ 연결 단서/참조 태그│
│ ...               │                          │ 연결 추리문        │
│ 기록 A            │                          │                    │
│ 기록 B            │                          │             루메   │
└───────────────────┴──────────────────────────┴────────────────────┘
```

최소 분류:

- 전체
- 현장 기록
- 증거
- 증언
- 통신·방송 기록

구현에서 더 세분화할 수 있으나 현재 정본을 깨는 중복 분류를 만들지 않는다.

### 5.3 음성 자료 계약

실제 음성 파일을 넣지 않는다.

금지:

- 오디오 파일 재생
- 재생/정지 버튼
- waveform
- 오디오 플레이어 UI

방송/통화/녹취 자료도 플레이어에게 다음과 같은 **텍스트 기록**으로 제공한다.

```text
기록 상황
→ 확인된 내용
→ 필요한 경우 짧은 발췌
→ 출처 / 시간 / 획득 정보
```

권장 플레이어-facing 명칭:

- 방송 기록
- 녹취 기록
- 음성 기록 요약
- 기록 내용

### 5.4 연결 정보

- 관련 키워드는 이미 획득한 것만 표시한다.
- `관련 키워드`보다 `연결 단서` 또는 `참조 태그` 같은 비정답성 표현을 우선한다.
- 기록에서 특정 매뉴얼 위치로 가는 `[괴이 매뉴얼에서 보기]` 같은 단순 링크는 허용한다.
- 링크는 정답 적합도나 추천을 의미하지 않는다.
- 매뉴얼에서 기록으로 돌아오면 기존 기록 선택/스크롤 문맥을 복원한다.

### 5.5 기록 상태 표현

허용:

- NEW
- 미열람/열람
- 획득 시간
- 출처

금지:

- 정답 단서
- 중요도 랭크로 사실상 정답 우선순위 제시
- 슬롯 적합도
- 변조 후보 식별

## 6. 괴이 매뉴얼 탭

### 6.1 화면 분리

```text
ManualTab
├─ ManualSectionIndex          ← 좌측
├─ DeductionWorkspace          ← 중앙 핵심
│  ├─ SectionHeader
│  ├─ DeductionDocument
│  │  └─ DeductionSlot × N
│  └─ HypothesisPanel
└─ ManualSideRail              ← 우측
   ├─ KeywordCandidateGrid
   └─ LumeCompanion
```

PC/태블릿/휴대폰 가로 모두 이 영역의 **의미와 순서를 동일하게 유지**한다.

### 6.2 좌측 섹션 인덱스

플레이어-facing 순서는 고정한다.

1. 발생 조건
2. 피해자 연결
3. 금지 행동
4. 구출 절차
5. 회수 대응

이는 5개의 독립 사건 장이 아니라 3장 로직을 플레이어 친화적으로 세분화한 UI 섹션이다.

### 6.3 중앙 DeductionWorkspace

화면의 주 콘텐츠는 장문 `추리문`이다.

- `추리문 01`, `추리문 02` 등 읽기 중심
- 본문 속 `『①』`, `『②』`, `『☆⑤』` 같은 슬롯
- 핵심 슬롯 표시가 있더라도 정답 단서로 작동하지 않음
- 하단에는 **`추리 가설`만** 둔다.

사용하지 않는다.

- 발생매커니즘 상세
- 추리 가설 확장
- 관련 키워드 별도 섹션
- 페이지 검토

### 6.4 5섹션과 기존 슬롯 수

기존 실제 진행 장 총 슬롯 수를 유지한다.

- 기존 1장 총 4슬롯 → UI 섹션 1·2에 분할
- 기존 2장 5슬롯 → UI 섹션 3
- 기존 3장 5슬롯 → UI 섹션 4
- UI 섹션 5 → 기본적으로 새 조사 슬롯 없음

섹션 1과 2 사이의 정확한 4슬롯 분배는 아직 미승인이다.

### 6.5 후보 키워드

우측 후보 키워드 카드는 획득/해금된 현재 문맥 후보만 표시한다.

다음은 모두 시각적으로 동일한 후보 카드 계층을 사용한다.

- 정상 후보
- 보조 후보
- 그럴듯한 오답
- 변조 후보

정답/오답/변조 상태를 색, 경고, glitch, 아이콘, 정렬 우선순위로 누설하지 않는다.

### 6.6 키워드 입력 계약

주 입력은 **선택 후 선택**이다.

두 순서를 모두 지원한다.

```text
슬롯 선택 → 키워드 선택 → 배치
키워드 선택 → 슬롯 선택 → 배치
```

배치된 슬롯:

- 다른 키워드 선택으로 교체 가능
- 명시적 비우기/취소 조작 가능
- 이전 섹션/페이지도 조사 종료 전 기존 도메인 계약 범위에서 수정 가능

드래그앤드롭은 선택적 보조 입력이다.

### 6.7 플랫폼별 완결 입력

- PC: 클릭만으로 완결
- 휴대폰/태블릿: 탭만으로 완결
- 키보드/게임패드: 포커스 이동 + 결정/취소로 완결

정밀 드래그나 긴 누르기를 필수로 요구하지 않는다.

### 6.8 UI와 판정 분리

Manual UI는 다음 의미의 사용자 의도만 전달한다.

- slot selected
- keyword selected
- placement requested
- replacement requested
- clear requested
- section navigation requested

실제 정답 여부와 장 완료/사건 진행 판정은 기존 도메인이 소유한다.

## 7. 지도 탭과 이동

### 7.1 지도 구성

지도는 현대 GPS가 아니라 **어두운 기록국식 역 구조도/청사진** 표현을 사용한다.

권장 의미 영역:

```text
좌측: 장소/층/구역 계층
중앙: 역 구조도 + 장소 마커
우측: 선택 장소 상세 + 상태 + [이동]
```

플랫폼이 달라도 이 정보 순서를 바꾸지 않는다.

### 7.2 장소 선택

지도 마커/장소를 한 번 선택했다고 즉시 이동하지 않는다.

```text
장소 선택
→ 장소명 + 짧은 설명 + 현재 상태 표시
→ 명시적 [이동]
→ shared travel request
```

터치 오탭을 즉시 장면 이동으로 연결하지 않는다.

### 7.3 장소 상태

같은 의미 체계로 표현한다.

- 현재 위치
- 방문 여부
- 새 조사 가능 여부
- 이동 가능 여부
- 잠금 상태
- 공개 가능한 잠금 이유

잠긴 장소는 기본적으로 사라지게 하지 않고, 공개 가능한 범위에서 잠금 상태/이유를 표시한다.

### 7.4 두 개의 이동 진입점

#### 지도

```text
[지도]
→ 장소 선택
→ 장소 상세
→ [이동]
```

#### 현장

```text
현장 조사
→ [이동]
→ 장소 선택
→ 장소 상세
→ [이동]
```

두 진입점은 동일한 location data와 동일한 domain travel handler를 사용한다.

금지:

- Map 전용 이동 로직
- Field 전용 이동 로직
- 서로 다른 장소 ID
- 서로 다른 잠금 판정
- UI가 이동 성공을 미리 추정

이동 성공 시 선택 UI/Shell을 닫고 새 장소 현장 조사 Surface로 진입한다.

## 8. 루메

### 8.1 명명

플레이어-facing 기능/캐릭터 명칭은 **`루메`**로 고정한다.

사용하지 않는다.

- AI 로그
- 로그 탭
- 독립 AI 화면

### 8.2 역할

루메는 **조사 보조 캐릭터**다.

허용:

- 이미 획득한 정보의 재확인
- 현재 화면 기능 사용 안내
- 분위기/사건 반응
- 짧은 캐릭터 코멘트

금지:

- 정답 알려주기
- 올바른 키워드 알려주기
- 정오 판정
- 근접도
- 추천 슬롯
- 미획득 단서 공개
- 변조 후보 판별
- 지도 최적 장소 추천
- 사건 해결 절차 대행

### 8.3 화면별 노출

기록:
- 우측 하단 compact 루메 기본 표시

괴이 매뉴얼:
- 우측 하단 compact 루메 기본 표시

지도:
- 상시 표시하지 않음
- 장소 상세를 선택했을 때만 짧은 contextual comment 허용

현장 조사:
- 평소 숨김
- 새 비정답성 코멘트가 있을 때만 작은 호출 표시

### 8.4 외형

CASE-01은 승인된 저승역 루메 디자인을 사건 대표 외형으로 사용한다.

후속 사건은 동일 캐릭터 정체성과 기능 역할을 보존한 범위에서 사건별 외형 콘셉트가 달라질 수 있다. 구체 자산 승격은 별도 아트 승인 대상이다.

## 9. 화면 방향과 해상도 대응

### 9.1 지원 방향

- PC: 가로
- 태블릿: 가로
- 휴대폰: 가로

휴대폰 세로는 주요 지원 레이아웃으로 취급하지 않는다.

### 9.2 동일 화면구성 원칙

플랫폼마다 정보를 drawer/bottom-sheet로 재배치하지 않는다.

예: 괴이 매뉴얼은 모든 지원 플랫폼에서

```text
좌측 섹션 인덱스 / 중앙 추리문 / 우측 후보·루메
```

의 의미 구조를 유지한다.

### 9.3 작은 화면 대응 우선순위

1. 안전 여백
2. 폰트 크기 범위
3. 패널 최소 폭
4. 영역별 독립 스크롤
5. 적절한 UI scale
6. 터치 타깃 확대
7. 텍스트 줄바꿈/ellipsis 정책

정보 영역 자체를 다른 위치로 옮기는 것은 기본 대응책이 아니다.

정확한 픽셀/최소폭/폰트 수치는 구현 전 별도 Visual QA에서 정한다.

## 10. UI 상태와 도메인 상태 경계

### 10.1 UI가 소유해도 되는 상태

- 어떤 탭이 열렸는가
- 어떤 목록/섹션/장소가 선택됐는가
- 스크롤 위치
- 지도 view position/zoom
- 키보드/게임패드 의미 포커스
- 아직 action request로 확정되지 않은 선택 강조
- 루메 compact/open 표시 상태

### 10.2 UI가 권위로 소유하면 안 되는 상태

- 실제 단서 획득 여부의 원본
- 키워드 진실/오답 여부
- 변조 판정
- 조사 성공 판정
- 장 완료 판정
- 장소 잠금의 원본 규칙
- 이동 성공 여부
- 사건 시간/비용
- 피해자 상태
- 전투/구출 진실

이 값들은 기존 domain/runtime 권위를 읽어서 렌더한다.

### 10.3 영속화 경계

어떤 UI view state를 save 파일까지 영속화할지는 아직 승인하지 않았다.

Shell이 열린 동안 또는 같은 플레이 세션에서의 상태 보존은 필수다. 세이브/로드를 넘는 영속화는 구현 계획에서 현재 저장 계약과 함께 결정한다.

## 11. 개념 데이터 계약

아래는 **책임 경계 설명용 개념 모델**이며 실제 클래스/필드 이름 승인이 아니다.

### 11.1 Record projection

```text
record_id
category
player_title
body_text
acquired_at / acquired_context
source
related_person_ids
related_location_ids
acquired_keyword_refs
related_manual_refs
read_state
```

오디오 바이너리/재생 URL은 이 UI 요구사항에 필요하지 않다.

### 11.2 Manual projection

```text
section_id
logic_chapter_id
section_title
deduction_document
slot_refs
candidate_keyword_refs
hypothesis_text
section_state
```

`section_id`와 `logic_chapter_id`를 개념적으로 분리해야 5섹션 UI와 기존 3장 진행을 혼동하지 않는다.

### 11.3 Location projection

```text
location_id
player_name
short_description
map_group / floor
current
visited
investigation_available
travel_available
locked
public_lock_reason
map_marker_metadata
```

지도와 현장 이동 UI가 같은 projection/권위를 사용해야 한다.

### 11.4 Lume projection

```text
context_surface
comment_id
comment_text
availability
read_state
```

정답 데이터, answer fitness, hidden clue, mutated truth 같은 필드를 UI 표현을 위해 노출하지 않는다.

## 13. 추리 공정성 UI 계약

UI는 플레이어 대신 답을 판별하지 않는다.

특히 후보 키워드/단서/지도/루메에서 다음을 금지한다.

- 정답만 다른 색
- 오답 빨간색
- 변조만 glitch
- 올바른 키워드 특별 아이콘
- 정답 적합도 퍼센트
- 근접도
- 추천 슬롯
- 자동 후보 축소
- 반복 오답 기반 정답 힌트 누적
- 지도에서 정답 장소 강조

선택, hover/focus, disabled/locked, NEW/read 같은 **상호작용/획득 상태**는 표현할 수 있지만 진실 상태와 혼동되지 않게 해야 한다.

## 17. 현재 구현과의 변환 경계

현재 `scripts/scenes/investigation_scene.gd`에는 CASE-01 조사 화면에서 다음과 같은 책임이 이미 한 파일/화면에 섞여 있다.

- `LocationPreview`
- 현장 대화
- 조사 포인트/방법
- 팀 상태
- record drawer
- manual panel/drawer
- log guide 관련 요소

새 Spec은 이를 즉시 삭제하라는 뜻이 아니다.

구현 단계에서는 다음 원칙으로 안전하게 이행한다.

- 현장 조사 동작을 먼저 보존한다.
- 기존 기록/매뉴얼 데이터를 새 Shell이 읽는 thin adapter 경로를 설계한다.
- 독립 로그/AI 로그 플레이어-facing UI는 새 정본으로 승격하지 않는다.
- 기존 GameState/domain 판정을 새 UI가 복제하지 않는다.
- 기존 테스트를 무시하고 화면만 교체하지 않는다.
- migration은 단계별로 진행하고 각 단계에서 기존 조사 진행 회귀를 검사한다.

## 18. 필수 테스트 계약

실제 구현 계획에는 최소 다음 테스트가 포함되어야 한다.

### 18.1 Shell

- 상단 탭이 `[기록][괴이 매뉴얼][지도]`만 제공된다.
- 로그/AI 로그 독립 탭이 없다.
- 탭 전환으로 게임 시간/판정/조사 진행이 바뀌지 않는다.
- `[현장으로 돌아가기]` 후 기존 조사 문맥이 복구된다.
- 재개 시 마지막 탭이 복구된다.

### 18.2 기록

- 방송/녹취 기록에 오디오 플레이어/파형이 없다.
- 텍스트 기록만으로 내용을 확인할 수 있다.
- 미획득 키워드가 연결 정보로 노출되지 않는다.
- 매뉴얼 링크 후 돌아와도 선택/스크롤 문맥이 유지된다.

### 18.3 괴이 매뉴얼

- 5개 UI 섹션이 보인다.
- 5개 UI 섹션 때문에 실제 진행 장이 5개로 늘어나지 않는다.
- 기존 총 슬롯 4/5/5 계약이 보존된다.
- 섹션 5가 새 필수 조사 슬롯/완료 게이트를 만들지 않는다.
- 정답/오답/변조 후보가 시각적으로 누설되지 않는다.
- PC 클릭만으로 배치/교체/비우기가 된다.
- 휴대폰 탭만으로 배치/교체/비우기가 된다.
- 키보드/게임패드로 같은 기능을 완결할 수 있다.
- 드래그를 하지 않아도 추리를 완료할 수 있다.

### 18.4 지도/이동

- 지도 장소 선택만으로 즉시 이동하지 않는다.
- 장소 상세 후 `[이동]`을 눌러야 travel request가 발생한다.
- 현장 `[이동]`과 지도 `[이동]`이 같은 location ID와 travel domain 결과를 사용한다.
- 잠긴 장소가 공개 가능한 이유와 함께 일관되게 표시된다.
- 이동 실패를 UI가 성공으로 오표시하지 않는다.

### 18.5 루메

- 기록/매뉴얼 compact 노출 규칙이 적용된다.
- 지도는 장소 상세 선택 때만 contextual comment가 가능하다.
- 현장에서는 상시 본체가 없다.
- 루메가 정답/추천/변조/미획득 단서를 말하지 않는다.

### 18.6 화면/입력

- PC/태블릿/휴대폰 가로에서 영역 순서가 동일하다.
- 휴대폰에서 핵심 UI를 drawer/bottom-sheet 전용 구조로 바꾸지 않는다.
- 오버레이 뒤 현장 버튼이 눌리지 않는다.
- 장식/투명 Control 때문에 필요한 포인터 입력이 막히지 않는다.
- 주요 포커스 순환이 끊기거나 갇히지 않는다.

### 18.7 Visual Requirement Gate

실제 구현 완료 판정 전에 최소 다음 실제 렌더 캡처를 검수한다.

- 현장 조사
- 기록 탭
- 괴이 매뉴얼 섹션 1/2/3/4/5 상태
- 지도 장소 미선택/선택/잠금 상태
- 루메 compact/contextual/call 상태
- PC 기준
- 휴대폰 가로 기준

스크린샷 검수 없이 레이아웃 완성으로 간주하지 않는다.

## 20. 완료 정의

이 통합 Spec 기준 CASE-01 UI 구현은 다음을 모두 만족해야 완료 후보가 된다.

1. 현장 조사와 조사 디바이스 책임이 분리되어 있다.
2. 조사 디바이스 상단은 기록/괴이 매뉴얼/지도만 가진다.
3. 기록은 텍스트 조사 아카이브이며 실제 오디오 재생을 요구하지 않는다.
4. 괴이 매뉴얼은 5개 UI 섹션을 쓰되 기존 3장 사건 로직을 보존한다.
5. 후보 키워드는 정답을 시각적으로 누설하지 않는다.
6. 마우스/터치/키보드·게임패드로 추리를 완결할 수 있다.
7. 지도와 현장 이동은 동일한 장소 데이터/이동 판정을 사용한다.
8. 루메는 독립 로그가 아니며 정답을 알려주지 않는다.
9. PC/태블릿/휴대폰 가로가 동일한 화면 구성 의미를 사용한다.
10. 탭/화면 전환이 조사 문맥을 불필요하게 잃게 하지 않는다.
11. 기존 domain truth와 저장/진행 규칙을 UI가 복제하지 않는다.
12. 자동/수동 테스트와 실제 렌더 Visual Gate를 통과한다.

이 문서가 사용자 검토로 승인되기 전에는 Godot 제품 변경을 시작하지 않는다.
