## 1. 목적

기존 프로젝트의 실제 Scene·Script·데이터와 최근 승인 기획을 연결해 다음을 한 정본에서 답한다.

1. 플레이어가 각 단계에서 무엇을 보는가?
2. 무엇을 판단하고 무엇을 입력하는가?
3. 시스템은 어떤 상태를 읽고 무엇을 바꾸는가?
4. 다음 화면은 어디이며 어떤 저장 체크포인트를 남기는가?
5. 현재 구현과 승인 목표의 차이는 무엇인가?

이 문서는 제품 구현 계획이 아니다. 화면·상황·상태·전환·저장·테스트의 기획 계약이며, 사용자 승인 전 제품 파일을 변경하지 않는다.

## 2. 근거 수준 표기

모든 항목은 다음 표기를 사용한다.

- `CURRENT_IMPLEMENTATION_LEGACY`: 현재 main에서 실제 동작하는 과거 계약
- `APPROVED_TARGET_NOT_IMPLEMENTED`: 사용자 승인 완료, 제품에 미구현
- `RECOMMENDED_DRAFT`: 이번 문서에서 제안하며 사용자 검수가 필요한 내용
- `INFERRED`: 기존 구조와 승인안에서 도출했지만 직접 구현 근거가 없는 내용
- `EXCLUDED_FROM_VALIDATION`: 기존 기능은 보존하지만 Validation 제품 경로에서 비노출
- `PLACEHOLDER`: 시각화·레이아웃 검토용이며 제품 권위가 없는 내용

CURRENT와 목표안을 같은 화면처럼 혼합하지 않는다.

## 3. 공통 제품 계약

### 3.1 플랫폼·입력

- 현재 플랫폼: `PC_CURRENT`
- 기준 비율: 16:9
- 검토 해상도: 1280×720 / 1920×1080
- 기본 입력: 마우스·키보드
- 모든 주요 행동은 키보드 포커스와 포인터 입력으로 실행 가능해야 한다.
- 색상만으로 선택·잠김·성공·실패·미해결 상태를 구분하지 않는다.

### 3.2 일반 플레이 표면

일반 조사·대화·일상 서사는 텍스트 노벨 방식이다.

```text
장소 배경
+ 상황 서술 또는 대사
+ 필요할 때 인물 초상
+ 2~4개 관찰·대화·행동 선택지
+ 선택 결과 문장과 기록 변화
```

자유 이동형 탐색 HUD를 기본값으로 사용하지 않는다. 가설 보드·시간순 증거·노선 복원·회수처럼 조작 책임이 다른 단계만 전문 화면으로 전환한다.

### 3.3 시각 언어

- 다크 현대 오컬트
- 현대 서울·기록국·역사 공간
- 세미리얼 애니 일러스트
- 성인형 슬림 비율의 기관 요원
- 남색·흑색·회색 기반, 역할별 제한 포인트 색
- 기록 문서·관제 패널·현장 장비를 결합한 UI
- 초현상 발광은 정보와 위험 강조에만 제한적으로 사용

SCREEN-01 메인에는 캐릭터·실루엣을 전면 표시하지 않는다.

### 3.4 상태 소유 원칙

- 화면은 표시와 사용자 의도 수집을 담당한다.
- 공통 상태는 `GameState` 또는 후속 승인된 상태 소유자가 담당한다.
- 재사용 UI 컴포넌트는 `GameState`를 직접 수정하지 않는다.
- 화면 전환은 명시된 Signal·라우터를 통해 처리한다.
- 전문 화면 종료 뒤 복귀 위치를 화면 내부 추측으로 결정하지 않는다.

### 3.5 Validation 노출 범위

전면 노출:

- 축약 준비 1회
- 텍스트 노벨 조사
- 사건 원인 가설
- 시간순 증거 비교
- 안전 노선 복원
- 회수 2패턴
- 결과 4축과 최소 환류

비노출:

- 랜덤 이벤트
- 세력 의뢰
- 소문시장
- 일상 에피소드
- 전체 4주 운영
- 복잡한 관계·확률·자동 행동 상세
- 회수 패턴 3·4
- 전체 연구 트리와 전체 조달 카탈로그

숨긴 기능은 판정·난수·로그·자원·관계·위험·저장 상태를 변경하지 않는다.

## 5. SCREEN-01 메인 화면

### 5.1 책임

- 새 Validation 캠페인 시작
- 저장된 진행 이어하기
- 기록국 DB 진입
- 접근성 설정 진입
- 저장 상태·오류 표시

### 5.2 CURRENT_IMPLEMENTATION_LEGACY

현재 `scripts/ui/main_menu.gd`는 다음을 제공한다.

- 저승역 입구·승강장 배경
- 타이틀·버전·장르 소개
- 첫 기록 저승역 미리보기
- 새 캠페인 시작
- 이어하기
- 기록국 DB
- 접근성 슬라이더
- F1 개발 패널

새 캠페인은 저장을 초기화하고 저승역 흐름을 재시작한 뒤 대화 Scene으로 직접 이동한다.

### 5.3 APPROVED_TARGET_NOT_IMPLEMENTED

- 캐릭터 전신·반신·실루엣을 표시하지 않는다.
- 빈 기록국·무인 역사·도시 야경·비정상 신호로 장르를 전달한다.
- 새 캠페인은 저승역 콜드 오픈으로 진입한다.
- 이어하기는 저장된 `flow_stage`를 기준으로 복귀한다.

### 5.4 RECOMMENDED_DRAFT 레이아웃

```text
[전체 배경: 무인 역사 또는 기록국 관제실]

          괴이기록국
     현대 오컬트 조사 기록

[새 기록 시작]
[이어하기: 저승역 / 조사 단계]
[기록국 DB]
[설정·접근성]

하단: 저장 시각 / 현재 사건 / 오류·호환 상태
```

### 5.5 상태 변형

1. `FIRST_RUN`
   - 이어하기 비활성
   - 새 기록 시작이 첫 포커스
2. `SAVE_AVAILABLE`
   - 이어하기에 사건명·단계·저장 시각 표시
3. `LEGACY_SAVE_AVAILABLE`
   - 레거시 진행임을 표시하고 기존 복귀 경로 사용
4. `SAVE_RECOVERABLE`
   - 일부 임시 화면 상태를 버리고 마지막 안전 체크포인트로 복귀
5. `SAVE_INCOMPATIBLE`
   - 저장을 자동 삭제하지 않고 오류 설명·백업·새 시작 선택 제공
6. `LOADING`
   - 입력 중복 방지, 짧은 상태 문구 표시

### 5.6 전환

- 새 기록 시작 → `SIT-001`
- 이어하기 → `Resume Router`
- 기록국 DB → 기존 DB 화면
- 설정 → 화면 내 Dialog 또는 설정 화면

### 5.7 Godot 경계

- 기존 `scenes/main_menu.tscn`과 `scripts/ui/main_menu.gd`를 제품 표면으로 유지하는 방향을 우선 검토한다.
- F1 개발 패널은 Debug build에서만 유지한다.
- 새 화면 프레임워크를 만들지 않는다.

### 5.8 검증

- 메인 화면에 캐릭터가 없는가?
- 새 시작과 이어하기가 서로 다른 초기화 규칙을 사용하는가?
- 손상 저장을 자동 삭제하지 않는가?
- 1280×720에서 핵심 버튼이 첫 화면에 보이는가?

## 6. SCREEN-02 텍스트 노벨 조사·일반 플레이

### 6.1 책임

- 장소와 상황 이해
- 대화·관찰·행동 선택
- 선택 결과와 기록 변화 확인
- 전문 화면 진입 조건 전달

### 6.2 CURRENT_IMPLEMENTATION_LEGACY

현재는 대화 Scene과 조사 Scene이 분리돼 있다. `investigation_scene`에는 다음이 공존한다.

- 배경과 상단 HUD
- 팀 상태
- 사건 요약
- 기록·설정
- 조사 포인트
- 조사 방법 선택
- 괴이 매뉴얼
- 회수 진입 버튼
- 결과 Toast

현행 구조는 재사용 가치가 있지만, 일반 텍스트 노벨 표면과 전문 추리 기능이 한 화면에 과밀하게 결합돼 있다.

### 6.3 APPROVED_TARGET_NOT_IMPLEMENTED

일반 플레이는 다음 순서를 기본으로 한다.

```text
상황 제시
→ 읽기
→ 관찰·대화·행동 선택
→ 결과 문장
→ 기록·상태 변화
→ 다음 텍스트 장면 또는 전문 화면
```

### 6.4 RECOMMENDED_DRAFT 레이아웃

```text
[장소 배경]

[상단 최소 정보]
사건명 / 현재 장소 / 기록 버튼 / 설정

[인물 반신 또는 빈 공간 연출]

[서술·대사 패널]
화자명
본문 2~6줄

[선택지 2~4개]
관찰한다
질문한다
기록을 확인한다
행동한다
```

상단에 수집률·회수 기준·자동 예측률을 상시 노출하지 않는다.

### 6.5 상태 변형

1. `NARRATION`
2. `DIALOGUE`
3. `OBSERVATION_CHOICE`
4. `ACTION_CHOICE`
5. `LOCKED_CHOICE`
6. `INLINE_RESULT`
7. `RECORD_DRAWER_OPEN`
8. `SPECIALIST_TRANSITION`
9. `RETURNED_FROM_SPECIALIST`
10. `SAVE_RECOVERY`

잠긴 선택지는 이유를 한 줄로 표시한다. 정답이 아니라 필요한 관측·기록·상태만 설명한다.

### 6.6 전문 화면 진입

- 사건 원인 정리 가능 → 가설 보드
- 시간순 기록 2개 확보 → 시간순 증거 비교
- 안전 경로 검증 필요 → 노선 복원
- 전문 화면 종료 → 명시된 텍스트 노벨 복귀 노드

조사 수집률만으로 회수에 직접 진입하지 않는다.

### 6.7 제외

- 기본 자유 이동
- 상시 전투 HUD
- 전문 화면을 같은 화면의 다중 탭으로 계속 유지
- 동료가 정답 선택지를 강조
- 회수 버튼의 조기 노출

### 6.8 Godot 경계

- 기존 `dialogue_scene`와 `investigation_scene`의 재사용 범위는 구현 계획 단계에서 결정한다.
- 기획 책임은 하나의 SCREEN-02로 통합하되, 실제 Scene을 반드시 하나로 합치지는 않는다.
- `ActionChoiceCard` 등 기존 반복 UI는 상태 비소유 원칙을 유지한다.

### 6.9 검증

- 첫 10분에 플레이어가 무엇을 읽고 무엇을 선택하는지 이해하는가?
- 전문 화면과 일반 조사 화면의 책임이 분리되는가?
- 결과 문장 없이 수치만 변하지 않는가?
- 기록을 다시 열어 판단 근거를 회수할 수 있는가?

## 7. SCREEN-03 축약 준비

### 7.1 책임

- 현재 사건 위험 확인
- 고정 주인공 확인
- 동료 최대 2명 선택 또는 추천 편성 확인
- 제한된 장비·지원 선택 1회
- 조사 우선순위 확인
- 출동 확정

### 7.2 CURRENT_IMPLEMENTATION_LEGACY

현재 `preparation_scene`은 다음 책임을 동시에 가진다.

- 권나래 중심 대시보드
- 오전·오후 반일 일정
- 현장 조사 / 대기·회복
- 일상 기록
- 외부 의뢰
- 사건 선택
- 일상 에피소드
- 요원 2~3명 편성
- 장비
- 외부 접점
- 기록

이 화면은 전체 제품 자산으로 재사용 가치가 높지만 Validation 준비 화면으로는 과밀하다.

### 7.3 APPROVED_TARGET_NOT_IMPLEMENTED

Validation에서는 일정·일상·외부 의뢰·소문시장 책임을 제거한다.

```text
현재 사건 확인
→ 추천 편성 확인 또는 동료 조정
→ 장비·지원 제한 선택
→ 조사 우선순위 확인
→ 출동
```

권나래는 고정 주인공이며 동료는 최대 2명이다.

### 7.4 RECOMMENDED_DRAFT 레이아웃

```text
[상단]
저승역 / 위험 단계 / 작전 목표 / 예상 소요

[좌측]
권나래 고정 카드
동료 2칸

[중앙]
출동 장비 1칸
지원 수단 1칸
조사 우선순위 1개

[우측]
이번 편성으로 달라지는 것
- 피해 완화
- 기록 비교 편의
- 재시도 조건

[하단]
추천 편성 복원 / 출동 확정
```

효과 설명은 `무엇이 편해지는가`를 보여주되 정답 가설·정답 행동·미관측 패턴을 공개하지 않는다.

3. `MISSING_REQUIRED_SLOT`
4. `ITEM_LOCKED`
5. `READY_TO_DEPLOY`
6. `CONFIRMING_DEPLOYMENT`
7. `RESUME_SUSPENDED_OPERATION`

### 7.7 제외

### 9.5 미래 일정 수정 규칙

- 실행 전 미래 날짜는 자유 수정한다.
- 이미 시작한 날짜와 완료한 날짜는 고정한다.
- 다일 활동은 전체 미실행 블록 단위로 이동·취소한다.
- 부분 완료된 다일 활동은 완료 일수를 보존한다.

### 9.6 돌발 출동 충돌 권장안

- 출동 발생 전날 또는 당일 실행 전: 미래 활동을 이동하거나 취소할 수 있다.
- 다일 활동 진행 중 출동: 완료된 날짜까지 진행을 보존하고 다음 날짜 경계에서 일시 중단한다.
- 출동 종료 뒤 남은 진행일을 다시 배치한다.
- 같은 날 중간 분할은 만들지 않는다.
- 강제 출동이 활동 보상을 소급 삭제하지 않는다.

- 관찰·대화·행동 선택지
- 선택 결과와 기록 갱신

### 플레이어 판단

어떤 정보가 관측 사실이고 어떤 것이 현상의 유도인지 구분한다.

### 입력

- 관찰·대화·행동 선택
- 기록 다시 열기

### 시스템 반응

- 필수 기록과 선택 기록 분리
- 핵심 기록은 수치·동료·장비로 잠그지 않음
- 선택 결과를 텍스트로 설명
- `flow_stage = investigation`

### 결과·다음 상황

필수 사건 기록 확보 → `SIT-005 가설·시간순 증거`

## 16. SIT-005 — 사건 가설과 시간순 증거

### 상황

플레이어가 사건 원인 가설 4개를 비교하고 두 개를 제거한 뒤 남은 두 가설을 시간순 기록으로 구분한다.

### 플레이어가 보는 것

- 가설 4개
- 증거별 지지·반박·미해결 관계
- 피해자 개인 목적지 청취 `23:57:42`
- 검은 승차권 최초 접촉 `23:59:08`

### 플레이어 판단

- 숨은 단일 종착역설 제거
- 전광판 전염설 제거
- 공백 투사설과 승차권 지정설 구분
- 승차권의 최초 원인 주장과 현장 매개 역할 구분

### 입력

- 가설 제거
- 증거 관계 연결
- 시간순 배열
- 최종 설명 제출

### 시스템 반응

- 행동 성공과 별개인 `causal_reasoning_state` 기록
- 오답은 정답 공개 대신 반박 근거와 미해결 관계를 보여줌
- `flow_stage = hypothesis`

### 결과·다음 상황

최소 안전 운용 질문이 남음 → `SIT-006 노선 복원`

## 17. SIT-006 — 안전 노선 복원

### 상황

플레이어가 공식 운행 기록과 현장 경로를 비교해 안전 이동 순서를 복원한다.

### 플레이어가 보는 것

- 노선·시간·방송 기록
- 조작형 복원 인터페이스
- 성공·실패 피드백

### 플레이어 판단

공식 식별 신호와 개인화된 목적지 신호를 구분한다.

### 입력

- 노선 순서 배치
- 검증 제출

### 시스템 반응

- 성공 여부와 등급 저장
- 실패해도 사건 전체 초기화 금지
- 재시도 또는 불완전 경로 상태 제공
- `flow_stage = route_validation`

### 결과·다음 상황

노선 결과 확정 → `SIT-007 회수 2패턴`

## 18. SIT-007 — 회수 패턴 1·2

### 공통 흐름

```text
전조
→ 패턴 분류
→ 관련 기록 연결
→ 중립 행동
→ 현장 결과
→ 추론 검증
```

### 패턴 1

- 이름: 존재하지 않는 종착 안내
- 분류 후보: 개인화된 경로 유도 / 새 노선 개통 / 표시 장치 단독 오류
- 행동: 승강장 스피커 전원을 내린다 / 표시된 방향으로 이동한다 / 현재 역명을 방송으로 송신한다

### 패턴 2

- 이름: 검은 승차권의 승객 각인
- 분류 후보: 접촉 대상을 승객으로 등록 / 인쇄된 목적지를 출력 / 봉인 절차를 요청
- 행동: 승차권을 격리 용기에 넣는다 / 개찰기에 통과시킨다 / 보호 봉투에 넣어 대표 요원이 보관한다

### 시스템 반응

각 패턴은 다음을 별도로 저장한다.

- 분류 선택
- 연결 기록
- 행동 선택
- 현장 성공
- 추론 검증
- 위험 사례

첫 Validation에서는 능력치 이름·성공률·동료 예측을 정답 신호로 노출하지 않는다.

### 결과·다음 상황

두 패턴 종료 → `SIT-008 결과·최소 환류`

## 19. SIT-008 — 결과 4축과 다음 영향

### 상황

플레이어가 사건이 어떤 상태로 끝났는지 확인한다.

### 플레이어가 보는 것

- 현장 안정화
- 피해자 구조
- 규칙 검증
- 괴이 핵·잔향 회수
- 검증된 기록·미해결 질문
- 연구 질문 1개
- 보급 후보 1개
- 다음 날짜 영향

### 플레이어 판단

올바른 행동과 올바른 설명이 같은 결과가 아님을 이해한다.

### 입력

- 결과 축 확인
- 사건 보고서 저장
- 최소 환류 확인
- Validation 종료

### 시스템 반응

- raw 결과 축 저장
- 요약 등급 계산
- 괴이 매뉴얼 갱신
- 연구·보급 후보 등록
- `flow_stage = validation_complete`

### 결과·다음 상황

- Validation: 완료 화면 또는 메인
- 전체 제품: SCREEN-05 다음 날짜

## 21. 저장·복귀 설계 초안

### 21.1 문제

현재 저장은 `current_scene_path`를 중심으로 이어하기를 처리한다. 전문 화면·모달·텍스트 노드가 늘어나면 Scene 경로만으로 의미 있는 복귀 지점을 판단하기 어렵다.

### 21.2 권장 상태

```yaml
campaign_mode: validation | legacy
flow_stage: main | cold_open | briefing | preparation | investigation | hypothesis | route_validation | recovery | result | validation_complete
current_screen_id: SCREEN-01..07
return_screen_id: optional
return_node_id: optional
checkpoint_id: stable transition checkpoint
validation_state:
  preparation_snapshot:
  investigation_progress:
  hypothesis_state:
  timeline_evidence_state:
  route_result:
  recovery_pattern_results:
  result_axes:
  post_result_candidates:
```

### 21.3 저장 체크포인트

- 새 캠페인 생성
- 콜드 오픈 종료
- 브리핑 종료
- 준비 확정
- 필수 조사 기록 획득
- 가설 제출 직전·직후
- 노선 결과 확정
- 회수 패턴별 결과 확정
- 결과 축 생성
- 보고서 저장

### 21.4 저장하지 않는 임시 상태

- Hover
- 버튼 눌림 애니메이션
- 일시적 Tooltip
- 미확정 드래그 위치
- 전환 Fade 진행률

### 21.5 호환

- 기존 `mvp-039` 저장은 `legacy`로 복원한다.
- 기존 저장을 새 Validation 단계로 억지 변환하지 않는다.
- 새 Validation 저장은 알 수 없는 선택 ID를 `orphaned`로 보존하고 효과 계산에서 제외한다.
- 손상 저장은 자동 삭제하지 않는다.

## 23. Godot 구조 권장안

새 범용 UI 프레임워크를 만들지 않는다.

- 기존 `Control` / `Container` / `Theme` 사용
- 반복 UI만 작은 Scene으로 분리
- `scripts/ui/`, `scripts/scenes/`, `scenes/` 구조 유지
- 안정된 상위 영역만 기존 런타임 편집 정책 적용
- 동적 목록 항목은 상태를 직접 소유하지 않음

화면별 구현 방향은 사용자 승인 뒤 별도 계획에서 결정한다.

## 24. 비주얼 보드 제작 계약

기획 승인 뒤 이미지는 한 장에 7개 화면을 작게 넣지 않는다.

- 보드 A: SCREEN-01~04 핵심 플레이
- 보드 B: SCREEN-05~07 운영·성장
- 상황 보드 C1~C4: SIT-001~008을 2개씩 묶어 큰 장면으로 표현
- 모든 화면에 `CURRENT / PROPOSED / PLACEHOLDER` 태그 표시
- 기술 부록은 메인 보드 뒤에 분리
