**일상(선택적 준비) → 사건 조사 → 불완전한 매뉴얼 작성 → 실제 규칙에 맞춰 구출·회수·미니게임 수행 → 결과와 귀환 반응**.

## 4. 작업별 설계·구현 명세

### W01 — 현재 정본과 호환 코드의 경계

- 현재 문제: AGENTS/기획·문맥 문서의 일정제 설명과 승인된 일상/사건 방향이 다르다. `campaign_state.gd`에는 day/time_slot/MAX_DAYS API가 남아 있다. 존재만으로 현재 UI가 이를 강제한다고 단정하지 않는다.
- 대상: `AGENTS.md`, `docs/CURRENT_PLANNING_CANON.md`, `docs/CURRENT_DECISION_OVERLAY.md`, `docs/PROJECT_CONTEXT.md`, `scripts/core/campaign_state.gd`, `scripts/core/game_state.gd` 및 실제 상속/override 체인.
- 절차: 각 일정 필드/메서드에 대해 읽기·쓰기·UI 노출·저장 migration·테스트 consumer를 추적한다. `ACTIVE_OWNER / COMPATIBILITY / ARCHIVE / UNKNOWN_UNVERIFIED`로 분류한다. 현행 설명은 일상/사건으로 정리하고 역사적 결정은 변경 이력으로 보존한다.
- 계약: 구형 저장의 날짜를 읽는 호환 기능은 남겨도 새 플레이의 출동/기본 지원을 날짜·휴식으로 제한하지 않는다. 제목/캐릭터 이름도 현행 제목과 루메로 통일하되 역사 기록은 강제 개명하지 않는다.
- 검사: 신규 시작에서 일상 생략 출동 가능; 구형 저장을 읽어 팀·기록·완료 결과 보존; 일정이 비어도 출동 가능; active UI에 잔여 일수 강제 노출 없음.
- 완료: 정본과 runtime consumer의 책임표 및 migration 회귀 PASS. 이름만 보고 API를 대량 삭제하지 않는다. 롤백은 문서/호환 수정의 독립 revert.

### W02 — 노트는 기억, 효과는 현장 행동

- 확인한 차이: `battle_scene.gd`의 `_evaluate_guided_decision()` 결과 `verified`가 `_resolve_recovery_clock_outcome()`에 전달된다. 따라서 초안/근거 선택에 의한 추가 효과 경로가 남아 있다.
- 설계: 추론 기록과 물리 판정을 분리한다. 기존 시도 기록에 가설·근거·선택 행동을 남기되 실제 대응 성공, 위험 완화, 안정화는 현장 상태/실제 행동/시점/장비에서 결정한다. UI는 관측 결과를 설명하고 '노트 정답 인증'을 성공 전제처럼 제시하지 않는다.
- 대상: `scripts/scenes/battle_scene.gd`, `scripts/core/game_state.gd`, `scripts/ui/anomaly_manual_drawer.gd`, `tests/recovery/manual_trial_feedback_test.gd` 및 guided/clock 테스트.
- 구현: 먼저 동일 상태·행동·시점에서 가설/근거만 다른 두 테스트를 RED로 만든다. 물리 effect 입력에서 논리 인증 값을 분리하고 기존 기본 효과량은 유지한다. 추가 완화는 실제 지원/행동 조건이 증명될 때만 허용하며 새 보너스 수치를 발명하지 않는다.
- 결과 데이터: 기존 history shape를 유지한다. 구형 `verified`는 당시 평가 metadata로 읽되 새 물리 효과를 재생하는 입력으로 쓰지 않는다. 새 데이터 필드가 필요하면 optional+default로 추가한다.
- 완료: 초안만 다르면 물리 결과 동일; 실제 규칙 행동이 다르면 결과 다름; 빈 초안도 행동 가능; 과거 결과 재열기가 현재 초안을 덮어쓰지 않음. 롤백은 저장을 손상하지 않는 정책 revert.

### W03 — M04 한 사건의 정상 플레이 완결

- 대상: `data/episodes/episode_002_red_umbrella_alley.json`, 대응 validation map, `investigation_scene.gd`, `manual_deduction_workbench.gd`, `minigame_scene.gd`, `rain_frame_sync_game.gd`, `battle_scene.gd`, `result_scene.gd`.

- 현재 작업으로 명확한 PR만 정확한 HEAD의 필수 검사·독립 검토·미해결 의견·ruleset을 확인해 안전하게 통합. direct main/force/admin 우회 없음.
- main에서 같은 핵심 회귀와 실행 아티팩트를 readback. 브랜치 기능 PASS를 main PASS로 옮겨 적지 않는다.
- 권리/출처/등급/배포 계약과 사람 최종 승인은 별도. 누락되면 RELEASE_BLOCKED_UNVERIFIED로 유지한다.
- 완료: 승인된 게임 범위의 W01–W11 잔여/보류/미검증이 재계산되고 user-testable 빌드와 알려진 제한 전달. 공개 배포는 자동 수행 범위로 간주하지 않는다.

## 5. 공통 테스트와 데이터 계약

새 중복 저장소/중복 정답 테이블을 만들지 않는다. 아래는 설계상의 역할 이름이며 존재하지 않는 새 API를 구현 완료로 표시하지 않는다.

| 역할 | 입력 | 출력/불변식 |
|---|---|---|
| 관측 기록 | source ID, 기존 원문 | 원본은 초안 수정으로 바뀌지 않음 |
| 매뉴얼 초안 | 획득 keyword ID, 슬롯/출처 | 플레이어 해석 저장; 정답 gate 아님 |
| 현장 판정 | 실제 행동, 전조/시점, 현장 상태, 기존 장비 | 물리 변화 + 관측 가능한 피드백 |
| 시도 이력 | 당시 초안과 행동, 수행 결과 | 재열기/초안 변경에도 당시 기록 보존 |
| 결과 확정 | 사건 실행의 기존 식별자, 구출/회수 결과 | 보상/의뢰/귀환 반응 한 번만 확정 |

테스트는 먼저 실패 재현→최소 수정→회귀→실제 화면 검증 순. 기존 테스트 파일을 우선 확장한다. 자료 초기화 fixture, 정상 UI 입력, 사람 플레이 증거는 서로 구분한다.

## 7. 검토·미검증·다음 실행

1차 명세 자체 검토: 기존 구현을 미구현으로 중복 배정하는 문제, 브랜치/main 혼동, 일정 호환 필드의 무조건 삭제, 사건 파일 수를 최종 분량으로 간주하는 오류를 점검해 상태/조건을 분리했다.

2차 명세 자체 검토: 노트 변경 보너스, 동시 성공 삭제, 정지 중 signal, 결과 중복 보상, 아트 생성=승인 오인, fixture=사람 검증 오인을 점검해 각 완료 조건에 반영했다. 이는 독립 코드 리뷰/게임 runtime CLEAN 선언이 아니다.

- `REMAINING_WORK_COMPLETION_GATE`: 위 12개 작업 패키지로 잔여를 관리. W09의 미확정 장기 콘텐츠는 구체 구현 READY가 아니라 SPEC_GATE.
- `IMPLEMENTATION_CORRECTION_RESCAN`: 먼저 W01/W02를 실행한 뒤 W03 정상 경로에서 새 결함을 재계산.
- `POST_COMPLETION_ADVERSARIAL_REVIEW_REQUIRED`: 각 구현 후 2회 전체 반례 검토와 실제 회귀 수행.
- `CLEAN_REVIEW_EXIT`: 이번 명세 자체의 알려진 모순을 교정했으며 게임 전체는 선언하지 않음.
- 다음 실행: W01 consumer 표 작성 → W02 비교 테스트 RED → 분리 구현 → W03 성공/실패 정상 입력 → W04/W05 경계 통합 → UI/아트/일상/다른 사건 순.

- 이번 요청 이후 runtime 코드/아트 수정은 수행하지 않았다. 문서 롤백은 이 명세와 handoff 항목만 되돌리며 기존 미커밋 테스트를 건드리지 않는다.
