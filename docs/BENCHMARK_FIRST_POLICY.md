# Benchmark-first 프로젝트 작업 원칙

> 상태: `APPROVED_PROJECT_WORKING_PRINCIPLE`
> 사용자 승인: 2026-07-31
> 추적: Issue #121 / Draft PR #122
> 적용 범위: `urban-legend`

## 1. 원칙

새 시스템, 핵심 규칙, 콘텐츠 구조, UX 흐름을 설계할 때는 설계안 작성 전에 반드시 벤치마킹을 수행한다.

목적은 다른 작품을 복제하는 것이 아니라 다음을 미리 확인하는 것이다.

- 유사한 플레이어 문제를 기존 사례가 어떻게 해결했는가
- 어떤 접근이 호평·불만·제작 비용·접근성 문제를 만들었는가
- 괴이기록국의 코어에 맞게 무엇을 채택·변형·제외할 것인가
- 설계 전에 발견할 수 있는 실패 위험이 무엇인가

## 2. Benchmark Gate 필수 대상

다음 중 하나라도 해당하면 Benchmark Gate를 적용한다.

- 새 플레이 시스템 추가
- 기존 시스템의 책임·입력·출력·보상·실패 구조 변경
- 괴이 조사·가설·미니게임·회수·육성의 핵심 규칙 변경
- 사건·에피소드·관계·연간 캠페인의 콘텐츠 구조 설계
- 주요 화면의 정보 위계·온보딩·입력·오류·복구 흐름 설계
- 제작 파이프라인과 콘텐츠 생산 비용을 크게 바꾸는 구조
- 플랫폼·장르·대상 플레이어·판매 범위를 바꾸는 결정

## 3. 대규모 조사 반복 방지

Benchmark-first는 매 작업마다 대규모 조사를 다시 수행한다는 뜻이 아니다.

### 기본 수행

- 이번 결정 질문에 직접 관련된 사례 3~5개만 우선 비교한다.
- 기존 프로젝트 벤치마크가 같은 질문을 다루고 현재에도 유효하면 `REUSED`로 재사용한다.
- 기존 자료에서 부족한 항목만 추가 조사한다.
- 조사 시간과 범위를 먼저 제한한다.
- 사례 수보다 적용·제외 결론을 우선한다.

### 범위 확장 조건

다음처럼 표본이 실제 의사결정에 필요한 경우에만 10개 이상 또는 시장 조사 수준으로 확장한다.

- 장르 정체성 변경
- 핵심 코어 교체
- 플랫폼 전환
- 가격·판매·출시 전략
- 대규모 UI·콘텐츠 제작 구조 변경
- 기존 벤치마크가 서로 충돌하거나 근거가 부족함

## 4. 반복 벤치마킹이 필요 없는 작업

다음은 기본적으로 `NOT_APPLICABLE`이다.

- 오탈자·문구·링크·경로 수정
- 구현 상태·Commit·PR·Sheet 정합성 동기화
- 승인된 설계를 그대로 구현하는 작업
- 플레이어 경험을 바꾸지 않는 명백한 버그 수정
- 동작을 보존하는 기술 리팩토링
- 테스트·회귀·문서 생성 보정

단, 위 작업이 결과적으로 플레이어 규칙·콘텐츠 구조·UX 흐름을 바꾸면 다시 필수 대상으로 전환한다.

## 5. 필수 산출물

Benchmark Gate를 적용한 기획은 최소한 다음을 남긴다.

```md
## Benchmark Gate

- 결정 질문:
- 기존 근거 재사용 여부:
- 비교 사례 3~5개:
- 반드시 반영:
- 조건부 반영:
- 제외:
- 주요 위험:
- 괴이기록국식 재해석:
- Gate 상태: PASSED / REUSED / BLOCKED
```

긴 조사 전문은 별도 연구 문서에 둔다. 기획서와 Issue에는 결정에 필요한 결론만 요약한다.

## 6. Gate 상태

| 상태 | 의미 |
|---|---|
| `PASSED` | 이번 질문을 위한 목적형 비교와 적용·제외 결론을 작성함 |
| `REUSED` | 기존 근거가 동일 질문과 현재 범위에 유효함을 확인함 |
| `NOT_APPLICABLE` | 신규 설계가 아닌 정정·실행·회귀 작업임 |
| `BLOCKED` | 필요한 근거가 부족해 설계를 확정할 수 없음 |

필수 대상이 `PASSED` 또는 `REUSED`가 아니면 다음 상태로 올리지 않는다.

- `APPROVED_DESIGN_BASELINE`
- `BUILD_READY`
- 구현 승인
- Codex Goal 작성·실행

## 7. 근거 품질

- 공식 페이지·개발자 발표·GDC·학술·전문 인터뷰를 우선한다.
- Steam·스토어·커뮤니티 반응은 마찰 신호로 사용하되 단독 정답으로 취급하지 않는다.
- 오래된 사례도 사용할 수 있으나 현재 플랫폼·대상 플레이어·프로젝트 방향과의 차이를 기록한다.
- 최신 사실이 필요한 시장·가격·플랫폼·지원 상태는 조사 시점에 다시 확인한다.
- 출처 없는 일반론만으로 신규 설계를 승인하지 않는다.

## 8. 프로젝트 적용 경계

벤치마킹 결과는 다음으로 변환한다.

```text
외부 사례 관찰
→ 플레이어 문제와 효과 추출
→ 괴이기록국 코어와 충돌 검토
→ 채택 / 조건부 채택 / 제외
→ 프로젝트식 규칙·데이터·UX로 재설계
→ 사람 검증 질문 작성
```

금지:

- 고유 UI·아트·캐릭터·서사·명칭 복제
- 인기만을 근거로 한 기능 추가
- 프로젝트 코어보다 외부 사례를 우선함
- 벤치마킹을 구현 범위 확대의 명분으로 사용함
- 조사 결과 없이 “업계 표준”이라고 단정함
