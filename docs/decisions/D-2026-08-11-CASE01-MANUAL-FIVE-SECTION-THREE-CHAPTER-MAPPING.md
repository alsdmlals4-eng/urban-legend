# D-2026-08-11-CASE01-MANUAL-FIVE-SECTION-THREE-CHAPTER-MAPPING

> 상태: `USER_APPROVED_CANON_CONFLICT_RESOLUTION / FIVE_SECTION_UI_OVER_THREE_CHAPTER_LOGIC / PLANNING_ONLY / IMPLEMENTATION_NOT_AUTHORIZED`
> 승인 시각: 2026-08-11 KST
> 적용 범위: CASE-01 저승역 괴이 매뉴얼의 플레이어-facing 5섹션 UI와 기존 3장 사건 로직의 대응
> Human/UI 검증: `NOT_RUN`

## 1. 배경

기존 제품 정본 `D-2026-08-04-AFTERLIFE-STATION-THREE-CHAPTER-MANUAL-AND-CANDIDATE-POOLS`는 저승역 괴이 매뉴얼을 실제 사건 진행 기준 3장으로 정의한다.

- 1장: 누가 목적지를 만드는가 — 4슬롯 / 후보 8
- 2장: 무엇이 반복을 일으키는가 — 5슬롯 / 후보 9
- 3장: 어떻게 현실로 데리고 나오는가 — 5슬롯 / 후보 10

이번 CASE-01 실제 게임 UI 시안은 좌측 매뉴얼 인덱스를 다음 5개 플레이어-facing 섹션으로 승인했다.

1. 발생 조건
2. 피해자 연결
3. 금지 행동
4. 구출 절차
5. 회수 대응

두 구조를 별개의 사건 로직으로 취급하면 기존 슬롯 수·후보 풀·최종장 완료·구출 진입 계약과 충돌하므로 다음 매핑으로 해소한다.

## 2. 승인 매핑

```text
기존 사건 로직 1장
├─ UI 섹션 1. 발생 조건
└─ UI 섹션 2. 피해자 연결

기존 사건 로직 2장
└─ UI 섹션 3. 금지 행동

기존 사건 로직 3장
└─ UI 섹션 4. 구출 절차

사건 후속 참조
└─ UI 섹션 5. 회수 대응
```

핵심 원칙은 **5개 UI 섹션이 5개의 독립 사건 진행 장을 뜻하지 않는다**는 것이다.

## 3. 기존 3장 정본 보존

다음 기존 계약은 유지한다.

- 총 실제 추리 진행 장은 3장이다.
- 장별 슬롯 총량은 기존 4 / 5 / 5 계약을 유지한다.
- 장별 후보 풀 상한/구조는 기존 8 / 9 / 10 계약을 유지한다.
- 현재 장의 필수 편집 조건과 다음 장 해금은 기존 도메인 진행 규칙을 따른다.
- 최종 실제 추리 장 완료 후 조사 페이즈 종료 확인을 거쳐 피해자 구출로 이어지는 흐름을 유지한다.
- 모든 빈칸이 채워졌다는 사실은 정답성을 의미하지 않는다.
- 세션 중 정답·오답·근접도·추천 순위는 공개하지 않는다.

이번 Decision은 기존 3장 정본을 폐기하지 않고 **표시 구조를 더 세분화한다**.

## 4. UI 섹션 의미

### 1. 발생 조건

- 기존 1장 내용 중 현상이 시작되는 조건·전조·관측 조건을 묶는 플레이어-facing 섹션이다.
- 독립적인 새 장 완료 판정을 추가하지 않는다.

### 2. 피해자 연결

- 기존 1장 내용 중 피해자 공통점·개인 목적지 투영·연결 조건을 묶는 플레이어-facing 섹션이다.
- 섹션 1과 함께 기존 1장 추리 상태를 표현한다.

### 3. 금지 행동

- 기존 2장의 반복/초기화/위험 행동 규칙을 표현한다.
- 기존 2장 진행 계약과 1:1로 대응한다.

### 4. 구출 절차

- 기존 3장의 현실 귀환 경로·승차권 대조·동행 탑승·올바른 하차 절차를 표현한다.
- 기존 3장 진행 계약과 1:1로 대응한다.

### 5. 회수 대응

- 새로운 조사 정답 장이 아니다.
- 조사에서 확립한 규칙이 이후 회수 단계에서 어떻게 참조되는지 보여주는 후속 읽기/참조 섹션이다.
- 이 섹션을 채우거나 편집해야만 피해자 구출 또는 조사 종료가 가능한 새 필수 조건을 추가하지 않는다.
- 회수 전투/후속 실행에서 읽기 전용 또는 단계별 갱신 참조가 될 수 있으나 구체 Schema와 시점은 후속 구현 Spec에서 정한다.

## 5. 플레이어-facing 인덱스 계약

괴이 매뉴얼 좌측 인덱스는 다음 순서를 유지한다.

```text
1. 발생 조건
2. 피해자 연결
3. 금지 행동
4. 구출 절차
5. 회수 대응
```

각 항목은 플레이어가 의미 단위로 문서를 찾기 위한 UI 분류다. 내부 데이터에서는 `logic_chapter_id`와 `section_id`를 분리할 수 있으나 실제 필드명은 구현 단계에서 결정한다.

## 6. 추리문·슬롯 계약

- 중앙 `DeductionDocument`는 현재 UI 섹션에 해당하는 추리문을 보여준다.
- `『①』`, `『☆⑤』` 같은 슬롯 표현은 UI 표현이며, 실제 슬롯의 정답성은 도메인이 소유한다.
- 섹션 분할 때문에 기존 총 슬롯 수를 임의로 늘리지 않는다.
- 기존 1장의 4개 슬롯을 섹션 1·2에 어떻게 분배할지는 콘텐츠 세부 Spec에서 정하되 총합은 4를 유지한다.
- 기존 2장 5개 슬롯은 섹션 3에, 기존 3장 5개 슬롯은 섹션 4에 대응한다.
- 섹션 5는 기본적으로 조사 추리용 새 슬롯 풀을 추가하지 않는다.

## 7. 후보 키워드 계약

- 후보 키워드는 기존 장별 후보 풀 권위를 따른다.
- 섹션 1·2는 같은 기존 1장 후보 풀의 문맥적 뷰를 공유할 수 있다.
- 동일 키워드는 비소모 참조이며 필요한 허용 위치에서 재사용할 수 있다.
- 정답 적합도·정상/변조 판별·추천 순서로 후보를 시각적으로 누설하지 않는다.

## 8. 충돌 해소 결과

이 Decision 이후 정본 해석은 다음과 같다.

- **사건 진행/콘텐츠 권위:** 기존 3장 Decision 유지
- **플레이어 UI 정보구조 권위:** 5개 섹션 인덱스 사용
- **슬롯/후보 총량:** 기존 3장 정본 유지
- **회수 대응:** 새 조사 장이 아닌 후속 참조 섹션

따라서 `5개 섹션 = 5개 사건 진행 장`으로 구현하는 것은 이 Decision 위반이다.
